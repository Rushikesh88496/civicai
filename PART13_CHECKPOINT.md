## What Was Implemented

**Deterministic engine (`app/services/routing_engine.py`)** — a pure, no-LLM router that
maps a complaint onto one of **seven fixed response departments** (`DepartmentCode`:
WATER, ROADS, ELECTRICAL, WASTE, DRAINAGE, PARKS, EMERGENCY_DISASTER) by fusing the
complaint's own category with the latest **triage / vision / priority / context**
signals:

- **Category matrix (`_CATEGORY_PRIMARY`)** — WATER & WATER_LEAK→WATER; ROAD→ROADS;
  ELECTRICITY & STREET_LIGHTING→ELECTRICAL; GARBAGE & SANITATION→WASTE; DRAINAGE →
  DRAINAGE; FLOODING→DRAINAGE; PARKS & FALLEN_TREE→PARKS; PUBLIC_SAFETY →
  EMERGENCY_DISASTER.
- **Multi-department rules** — FLOODING → primary **DRAINAGE** + secondary **[ROADS]**
  (`MAX_SECONDARY=2`); ELECTRICITY with fallen-infrastructure wording
  (`_ELECTRICAL_EMERGENCY_HINTS`: fallen, downed, exposed, spark, live wire, pole down,
  collapsed pole, broke, snapped) → primary **ELECTRICAL** + secondary
  **[EMERGENCY_DISASTER]**.
- **Unknown / OTHER** → `ambiguous=True`, primary fallback DRAINAGE, confidence
  `ROUTING_CONFIDENCE_UNKNOWN` (0.30), reason explains a human decision is advised.
- **Confidence** — single known = `ROUTING_CONFIDENCE_KNOWN` (0.92), multi =
  `ROUTING_CONFIDENCE_MULTI` (0.85), unknown = 0.30; **+0.03 boost** when triage/vision
  severity is HIGH/CRITICAL or the priority bucket is P1/P2; clamped ≤ 1.0, rounded 3
  decimal places. Always explainable (`routing_reason`).

**Agent (`app/agents/routing_agent.py`)** — LangGraph `START → compute → persist → END`,
`AGENT_NAME="routing"`, no LLM. `_latest_output` loads the latest per-agent run
(via the new `agent_run_service.get_latest_run_for_agent` helper) validated into
`TriageOutput` / `VisionOutput` / `PriorityOutput` / `ContextOutput`. `run(...)` mirrors
the priority agent (create_run, commit, invoke, duration, reload). Each decision persists
a `RoutingOutput` to `agent_runs` (`agent="routing"`) **and** appends a
`complaint_department_history` row.

**Effective department + overrides** — `_current_effective_department` lets an officer
override win over the latest routing. Each override writes `old_department`,
`new_department`, `reason`, `override_by`, and a timestamp to the append-only
`department_overrides` table. `complaint_tracking_service.get_effective_department`
surfaces the current department on the complaint detail (`GET /complaints/{id} →
department=...`), which is `override.new_department` if any, else latest routing
`primary_department` (else `None`).

**Model + Migration** — `DepartmentCode` enum + `DEPARTMENT_LABELS` dict in
`app/models/enums.py`; `ComplaintDepartmentHistory` (`complaint_department_history`) and
`DepartmentOverride` (`department_overrides`) models; `department_history` and
`department_overrides` relationships on `Complaint`; both registered in
`app/models/__init__.py`. Migration `be6083718a2c` (down_revision `b3c4d5e6f7a8`)
autogenerated then **manually rewritten** to strip spurious PostGIS/geometry /
`ix_complaint_correlations_decided_by` diffs (offline-metadata artifacts), applied and
verified; `alembic heads = be6083718a2c`.

**Schemas (`app/schemas/routing.py`)** — `RoutingInputs`, `RoutingOutput`, `RoutingRunOut`,
`RoutingRunResponse`, `RoutingRunIn`, `RoutingHistoryEntry`, `RoutingHistoryOut`,
`DepartmentOverrideIn`, `DepartmentOverrideEntry`, `DepartmentOverrideResponse`,
`DepartmentOverrideHistoryOut`.

**Service (`app/services/routing_service.py`)** — `RoutingNotFoundError` /
`RoutingAccessError`, `_assert_can_view` (uses `user_can_view`), `run_routing`,
`get_routing_result`, `get_routing_history`, `get_override_history`, `override_department`
(respects `ROUTING_OVERRIDE_ENABLED` and requires a reason).

**API (`app/api/v1/complaints.py`)** — `_routing_error` mapper (404/403/400) plus:
`POST /{id}/routing` (RoutingRunResponse), `GET /{id}/routing-result`
(RoutingRunOut | None), `GET /{id}/routing-history` (RoutingHistoryOut),
`POST /{id}/routing/override` (staff-only via
`require_roles(OFFICER, ADMIN, WARD_REPRESENTATIVE)`; returns DepartmentOverrideResponse),
`GET /{id}/routing/overrides` (DepartmentOverrideHistoryOut).

**Config (`app/core/config.py` + `backend/.env.example`)** —
`ROUTING_CONFIDENCE_UNKNOWN=0.30`, `ROUTING_CONFIDENCE_KNOWN=0.92`,
`ROUTING_CONFIDENCE_MULTI=0.85`, `ROUTING_CONFIDENCE_PRIORITY_BOOST=0.03`,
`ROUTING_MAX_SECONDARY_DEPARTMENTS=2`, `ROUTING_OVERRIDE_ENABLED=True`.

## Known Limitations / Remaining Issues
- The engine reads the latest triage / vision / priority / context runs, so the
  confidence boost and reason wording depend on those agents having run; without them it
  degrades gracefully (no boost, category-only reason) rather than failing.
- Category routing is deterministic and intentionally does **not** use an LLM — nuanced
  free-text categories sink to OTHER → ambiguous (a documented, safe default).
- Full-suite `pytest` still hangs under this host's memory pressure; suites are run
  per-file. Pre-existing S3/MinIO outage still blocks the media-upload tests — both
  unrelated to Part 13.

## Security
- No secrets introduced or logged. The router is fully deterministic — no LLM call, no
  external service, no credential. The override endpoint is restricted to
  OFFICER/ADMIN/WARD_REPRESENTATIVE (403 for citizens; 401 unauthenticated; 404 unknown
  complaint). Read endpoints enforce complaint ownership. Reason is required on an
  override; the audit trail is append-only with actor + timestamp. Overrides are tunable
  via `ROUTING_OVERRIDE_ENABLED`; no key is hardcoded.
