## What changed

**The core principle:** predictive civic hotspots are trained, must be trained, and can only be trained on **real complaint records stored in the database**. Complaint coordinates come exclusively from (1) the citizen's actual GPS fix or (2) an explicitly user-selected location on the manual map — never from a predefined, random, hardcoded, or demo generator. Zero complaints ⇒ zero hotspots: no hotspot markers, no heatmap, no "predicted" hotspot, and no fake complaint marker on any map. Simply opening the hotspot page never creates a model or a forecast.

### Backend

- **`app/ml/corpus.py`** — removed the seeded synthetic generator (`build_corpus`, `_poisson`, `_seasonal_rain`, `_static_cell_field`, `_category_weekly_weights`, monsoon/weekend/spatial-coupling logic). Kept the `ComplaintEvent` / `Corpus` data shapes and added `corpus_from_events(events)` — a pure container that sorts real events by timestamp. Nothing in the module fabricates a location.
- **`app/core/config.py`** — `HOTSPOT_CORPUS_YEARS` / `HOTSPOT_CORPUS_SEED` replaced by `HOTSPOT_TRAIN_LOOKBACK_DAYS=730` (how far back real history is drawn) and `HOTSPOT_TRAIN_SEED` (fit-variance only, never location generation). Comments now state training uses only real complaint records.
- **`app/ml/pipeline.py`** — bundle `config` now records `training_source="real_complaints"`, `training_description` (“No synthetic, random, hardcoded or demo complaint locations are used”), `training_lookback_days`, `train_seed`; dropped `corpus_years` / `corpus_seed` / `corpus_description`. Seed feeds only feature-dropout + XGBoost `random_state`.
- **`app/ml/external.py`** — docs updated: training and live inference both use the real provider (ward resident counts + currently available rainfall); nothing fabricates cells/coordinates.
- **`app/services/hotspot_service.py`** (main rework):
  - `_historical_events(db, grid, settings)` — loads **real** `Complaint` join `ComplaintLocation` rows within the training lookback, bucketed into grid cells; coordinates are the complaint's actual lat/lon.
  - `_readiness(...)` — real-complaint gating (Part 31): records = located complaints inside the grid; area-time observations = distinct (cell, day) buckets. Zero complaints ⇒ never ready.
  - Training span guard — real history must span at least `horizon + 40` days so rolling features and label windows are well-formed; shorter bursts return `INSUFFICIENT_DATA`.
  - **No lazy provisioning** — `get_predictions` no longer trains on first GET. A ready-but-untrained platform returns `prediction_status=READY`, `model=None`, `cells=[]`, and a message telling an authorized officer to run `POST /api/v1/hotspots/train`; the `predictive_models` registry stays empty.
  - **Real-source guard** — status/predictions refuse to serve any active model whose `config.training_source != "real_complaints"` (defense-in-depth against legacy synthetic artifacts).
  - **Crowd-centroid coordinates** — each reported hotspot's position is the mean of the actual live complaint coordinates in that cell (`_crowd_centroids`); the grid centroid is only a fallback for cells with no live events. Hotspot geography is therefore *calculated from real complaints*.
  - Training uses the real `LiveContextProvider` (ward residents + optional citywide rainfall), not the synthetic context provider.
- **Artifacts** — deleted committed synthetic-trained binaries `hotspot_v1..v8.joblib` from `app/ml/artifacts` (infrastructure artifacts untouched, out of scope).
